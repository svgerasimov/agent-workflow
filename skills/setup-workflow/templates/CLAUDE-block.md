## Процесс разработки с агентом

Процесс из `agent-workflow`. Пути, команды и правила этого проекта - в [docs/agents/workflow.md](docs/agents/workflow.md).

### Размер задачи

В начале агент одной строкой предлагает размер и почему, пользователь может поменять. По ходу вылезла интеграция или противоречия в ТЗ - предложить размер больше. Принятый размер - строкой `**Размер:** M` в шапке `00-intake-<feature>.md` и PRD: скиллы в новых сессиях берут его оттуда. Строки нет - считать L.

| | S - мелочь | M - обычная фича | L - тяжёлая |
|---|---|---|---|
| Признаки | баг, правка экрана, ТЗ нет или 1-2 стр. | новый экран или сервис, 1-2 ручки, ТЗ до ~10 стр. | ТЗ больше 10 стр., интеграции с внешними системами, деньги, несколько ролей |
| Разбор | сам, в чате: "как понял" + вопросы с цитатами | `/intake` лёгкий | `/intake` полный |
| Гриль | нет | `/grill-with-docs`, один круг | два круга |
| Схема решения | нет | `/solution-design`, только если новый модуль | `/solution-design` |
| PRD | нет | `/to-spec` короткий + `/spec-check` одним судьёй | `/to-spec` + `/spec-check` |
| Макеты | по скриншоту | спеки экранов, если есть экраны | спеки экранов |
| Тикеты | одна задача, без файла | `/to-tickets`, 2-5 | `/to-tickets` + `/ticket-check` |
| Сборка | `/tdd` или `/implement` лёгкий | `/implement`, лёгкий цикл где можно | `/implement` полный |

Во всех размерах: утверждения о ТЗ - с цитатой, вопросы - до кода, код - через тесты, `/code-review` перед коммитом.

### Полный пайплайн (L)

Всё до `/to-tickets` - в одной сессии, чтобы контекст разбора не потерялся.

```
ветка            → по правилу из workflow.md, номер тикета даёт пользователь
/intake          → два слепых аналитика (Opus) → скрипт проверки цитат → судья (Fable) → сортировка вопросов (Opus) → requirements.md (ТЗ-NNN) + 00-intake-<feature>.md → до 10 вопросов пользователю → ревизия макетов
/grill-with-docs → два круга: суть → GLOSSARY.md, реализация → решения для PRD, при необходимости ADR
/solution-design → solution-design.md со схемой, стоп на ручную проверку
/to-spec         → <папка фич>/<feature>/01-prd-<feature>.md
/spec-check      → судьи сверяют PRD с реестром ТЗ-NNN в обе стороны, заполняют "Где в PRD"; стоп по находкам
спеки макетов    → по каждому экрану из PRD
/to-tickets      → <папка тикетов>/<NN>-<slug>.md, вертикальные слайсы с критериями приёмки
/ticket-check    → в чистом контексте: тикеты против реестра и PRD; повторять, когда PRD менялся после нарезки
```

Дальше строго по одному тикету: `/implement <NN>` → объяснение задачи → швы и тесты → реализация → ручная приёмка → `/code-review` → коммит → `done/`.

`/spec-check` агент запускает сам сразу, как PRD записан: PRD пишется по горячему контексту гриля, и разделы ТЗ из него выпадают незаметно. Всё, где ТЗ молчит, противоречит себе или расходится с бэком и макетом, в PRD не решается по-тихому: допущение помечается `Д-N` и уходит в раздел "Допущения и несоответствия - на проверку аналитику" с колонками "что в ТЗ / что приняли / вопрос".

### Intake: понимание только из присланного

Понимание задачи - только из материалов, которые прислал пользователь (ТЗ, макеты, тикет, user stories). Ничего не искать снаружи и не достраивать. Код проекта - только чтобы понять, что уже есть, не как источник требований. Непонятное, недосказанное, противоречивое - вопрос пользователю до гриля и PRD.

Каждое утверждение о материалах - с дословной цитатой: файл, страница, короткая цитата, которую можно найти поиском. "По ТЗ стр. N" без цитаты - не доказательство. Нет опоры - пометка "догадка" или вопрос.

Прокол на любом шаге (неверно поняли ТЗ, выпало требование) - строка в [docs/agents/incidents.md](docs/agents/incidents.md) и в тот же день эвал-кейс скиллу, который должен был это поймать (`/intake`, `/spec-check`, `/ticket-check`), в клоне agent-workflow (`workflow.md`). Перед разбором новой фичи журнал пробежать.

### Формат общения

Вопросы на разборе и гриле - простым языком, как коллеге за столом: заголовок "что решаем", 2-4 обычных предложения о том, что это в продукте и почему вопрос встал, предложение своими словами и один простой вопрос в конце. Без обрывков фраз, без номеров и имён полей вместо объяснения. Один вопрос за раз. Не понял пользователь - сразу переобъяснить с контекстом, не ждать команды.

### Формат находки

Для всего, что выносится пользователю на решение (вопросы `/intake`, находки `/spec-check` и `/ticket-check`, расхождения на ревью). Находка объясняет себя сама: пользователь не держит фичу в голове и документы не открывает.

- **Заголовок** - что решаем, человеческими словами.
- **Что происходит в приложении** - экран, момент, что делает пользователь, 1-3 предложения.
- **Что написано в ТЗ** - дословно, со страницей; если условий несколько - все.
- **Что у нас** - PRD, тикет, код: дословно там, где расхождение.
- **В чём проблема** - одной-двумя фразами.
- **Чем грозит** - что увидит пользователь приложения, если оставить как есть.
- **Что предлагаю** - и почему; в конце один простой вопрос.

Номера (`ТЗ-`, `Д-`, номер тикета) - только в скобках после объяснения. По одной находке за сообщение; мелкая чистка без изменения поведения - одним списком в конце. Проверка перед отправкой: поймёт ли человек, не открывая ни одного документа.

### TDD

Любая фича или фикс с бизнес-логикой - red-green-refactor: тесты только на заранее названных швах, тест красный по правильной причине, минимальный код до зелёных, рефакторинг только на зелёных. Не писать код, а потом "докидывать тесты". Не подгонять assert под поведение кода.
