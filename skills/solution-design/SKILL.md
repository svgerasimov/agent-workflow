# Skill: solution design

Зачем: решения круга "реализация" на гриле иначе уходят только текстом в "Решения по реализации" PRD, плотными абзацами, которые глазами не проверить. Ошибку в архитектуре дешевле всего поймать до PRD и нарезки, а тикеты потом режутся по этой схеме.

Когда: после второго круга `/grill-with-docs`, до `/to-spec`. Размер L - всегда; M - только если появляется новый модуль; S - не нужен.

Пути проекта - в `docs/agents/workflow.md`. Все ответы - на языке пользователя, простыми словами.

## 1. Собрать

Только из того, что уже есть: решения гриля, глоссарий фичи, реестр `requirements.md` (если есть), код проекта - что уже есть для переиспользования. Новых требований не придумывать; дыра - вопрос пользователю.

## 2. Нарисовать

`<папка фич>/<feature>/solution-design.md`, диаграммы - mermaid:

1. **Путь данных**: экран → состояние или хук → слой API → ручка бэка и обратно. Каждый узел - реальный модуль или файл (новый - с будущим путём).
2. **Цветом**: новое / переиспользуем / не трогаем (`classDef new`, `reuse`, `keep` в mermaid).
3. **Где живёт логика**: слои и границы между ними, словарь - скилл `codebase-design` (модуль, интерфейс, шов). По строке на каждое правило из реестра: в каком слое считается.
4. **2-3 живых сценария**, прогнанных по схеме: "пользователь сделал X → что запрашивается, где считается, что он видит". Сценарий упирается в узел, которого нет на схеме, - схема неполная.

Если доступен инструмент публикации страниц (Artifact) - опубликовать ту же схему страницей, чтобы смотреть глазами, и дать ссылку.

## 3. Ручная проверка → ⛔ СТОП

Пользователю - три вопроса, каждый простыми словами:
1. Так ли идут данные?
2. Нет ли нового там, где можно взять готовое?
3. Лежит ли логика там, где ты ожидаешь?

Правки - в схему. Потом `/to-spec`; раздел "Решения по реализации" PRD ссылается на `solution-design.md`, а не пересказывает его.

## Чего не делать

- Не писать код и не нарезать тикеты.
- Не рисовать "идеальную архитектуру" сверх фичи: только то, что нужно этим сценариям.
- Не вводить новый слой или абстракцию без строки "зачем" и согласия пользователя.
