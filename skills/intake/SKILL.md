# Skill: intake - первичный разбор

Зачем: неверно понятая формулировка ТЗ отсюда уезжает дальше как факт - в глоссарий, PRD, задачи и код. Судьи `/implement` и ревью сверяют с задачей, а не с ТЗ, поэтому все следующие проверки её подтверждают. `/spec-check` после PRD ловит пропуски, но неверное прочтение хуже: судья видит его в PRD и соглашается. Ловить надо здесь, до гриля.

**Понимание задачи - только из присланного.** Ничего не искать снаружи и не достраивать. Код и глоссарии проекта - только чтобы понять, что уже есть, не как источник требований. Непонятное, недосказанное, противоречивое - вопрос пользователю, не догадка.

**Каждое утверждение о материалах - с дословной цитатой** (файл, страница, цитата). Цитаты проверяет скрипт, не модель.

Пути и команды проекта - в `docs/agents/workflow.md`. Нет файла - предложить `/setup-workflow` и остановиться. Скрипты лежат в папке этого скилла (`<папка скилла>/scripts/`, путь к папке Claude Code показывает при загрузке скилла).

Все ответы пользователю - на языке пользователя, простыми словами, как в "Формате общения" CLAUDE.md.

## Режим: лёгкий или полный

Размер задачи - по таблице S/M/L в CLAUDE.md. Агент предлагает одной строкой, пользователь может поменять.

**Лёгкий (M)** - без аналитиков, судей и сортировщика:
1. Шаги 0-1 как в полном.
2. Главная сессия сама читает материалы и пишет `00-intake-<feature>.md`: выжимка по экранам, у каждого утверждения дословная цитата со страницей; внизу вопросы. Требования - тем же JSON-форматом, что у аналитиков, в `intake/self.json`, чтобы прогнать скрипт.
3. `scripts/check-quotes.mjs` по `self.json`. Ненайденные цитаты - исправить или пометить "догадка".
4. Шаг 6 (до 10 вопросов: сначала то, что меняет сценарий или контракт с бэком, у каждого вариант по умолчанию) и шаг 7 (ревизия макетов) как в полном.

Реестр `requirements.md` в лёгком режиме - по желанию (`scripts/render-registry.mjs` понимает и `self.json`, если переименовать `requirements` в `registry`); без него `/spec-check` идёт в режиме ТЗ.

Перейти в полный, если по ходу: противоречий в ТЗ больше трёх, интеграция с внешней системой, ТЗ больше ~10 страниц.

**Полный (L)** - всё ниже.

## Роли

```
Оркестратор (главная сессия) - раздаёт, собирает, говорит с пользователем. Сам ТЗ не анализирует.
  ├─► Аналитик A (Opus) - по структуре ТЗ ─┐  оба видят только source/,
  ├─► Аналитик B (Opus) - по сценариям     ─┤  отдают JSON одного формата
  │                                         ▼
  │   scripts/check-quotes.mjs - каждая цитата есть в source/?
  │                                         ▼
  │   Судья (Fable) - сводит A и B, сверяет с ТЗ, ищет пропущенное → judge.json
  │                                         ▼
  │   check-quotes.mjs по judge.json - судья тоже не выдумывает
  │                                         ▼
  │   Сортировщик (Opus) - важность, кто ответит, вариант по умолчанию → triage.json
  ▼
requirements.md (реестр ТЗ-NNN) + 00-intake-<feature>.md → вопросы пользователю
```

Главная сессия не аналитик и не судья: она слышала разговор и смотрит на ТЗ через него.

Все субагенты - Agent tool, general-purpose, со свежим контекстом. Аналитики - `model: opus`, судья - `model: fable`. Модель недоступна (ошибка запуска) - сказать пользователю и запустить без override, не молчать.

## 0. Фича и папка

Ветка - по правилу из `workflow.md` (номер тикета даёт пользователь, не выдумывать). Папка - `<папка фич>/<feature>/` из `workflow.md`:
- `source/` - сырьё: PDF, скриншоты, JSON-ответы бэка. Что пользователь прислал в чат текстом - сохранить сюда файлом (`.md`), иначе субагенты его не увидят.
- `intake/` - рабочие файлы: `analyst-a.json`, `analyst-b.json`, `quote-check.json`, `judge.json`.

## 1. Подготовить источники

Для каждого PDF без соседнего `.txt`:

```
sh <папка скилла>/scripts/pdf-to-text.sh source/<file>.pdf > source/<file>.txt
```

Проверить, что текст не пустой и читается (грепнуть пару слов из заголовков). Страницы размечены `=== PAGE N`. Скриншоты - посмотреть самому и, если на них требования (комментарии к макету, тексты), переписать в `source/screens.md` с именем файла скриншота у каждого куска: скрипт проверяет цитаты только по тексту.

Оркестратор пробегает материалы, чтобы знать объём и разделы, но выжимку сам не пишет.

## 2. Два аналитика - параллельно

Запустить обоих в одном сообщении. Разговор, догадки оркестратора, глоссарий - не передавать. Только пути к файлам `source/` и задание.

ТЗ больше ~40 страниц - аналитика A резать на 2-3 параллельных по диапазонам страниц, по границам разделов, с нахлёстом в страницу; B идёт по всему документу.

**Общая часть задания (обоим, дословно):**

> Прочитай материалы фичи: <пути>. Текст из PDF размечен `=== PAGE N`, колонки таблиц могут быть перемешаны - условие фразы может оказаться строкой ниже. Ничего не додумывай и не бери из "обычной практики": если ответа в материалах нет - так и пиши.
>
> Каждое утверждение - с источником: `file` (имя файла), `page` (номер из `=== PAGE`, у файлов без страниц - null), `quote` - **дословная** цитата 5-25 слов, скопированная из текста, без пересказа. Пропуск внутри цитаты - `...`. Цитаты будут проверены скриптом поиском по тексту.
>
> Запиши результат в `<путь>/intake/analyst-<a|b>.json` строго в формате:
> ```json
> {
>   "analyst": "A",
>   "sources_read": [{ "file": "", "pages": "1-41", "status": "full | partial | unreadable", "note": "" }],
>   "requirements": [{
>     "id": "A-001",
>     "type": "screen | flow | rule | limit | text | field | integration | example | nfr",
>     "statement": "одно требование своими словами, одним предложением",
>     "sources": [{ "file": "", "page": 0, "quote": "" }]
>   }],
>   "ambiguities": [{ "id": "A-AMB-1", "sources": [{ "file": "", "page": 0, "quote": "" }], "readings": ["прочтение 1", "прочтение 2"], "why_it_matters": "чем отличаются для пользователя" }],
>   "conflicts": [{ "id": "A-CON-1", "sources": [{ "file": "", "page": 0, "quote": "" }, { "file": "", "page": 0, "quote": "" }], "note": "что с чем не сходится" }],
>   "missing_refs": [{ "id": "A-REF-1", "sources": [{ "file": "", "page": 0, "quote": "" }], "what": "на что ссылаются, а текста в материалах нет" }],
>   "coverage": [{ "section": "", "pages": "", "requirement_ids": [], "empty_reason": null }]
> }
> ```
> Одно требование - одна запись: правило, лимит, текст ошибки, поле, условие "если - то". Пример запроса или ответа из ТЗ - отдельная запись типа `example`, в `statement` - полный список ключей. Строка таблицы правил - отдельная запись. Кто формирует данные (приложение, бэк, внешняя система) - обязательно, отдельной записью, если ТЗ это говорит.
>
> В ответе мне - только путь к файлу и три числа: требований, двусмысленностей, противоречий.

**Аналитик A - по структуре ТЗ:**

> Иди по документу раздел за разделом, страница за страницей. `coverage` - по каждому разделу: какие записи из него, или `empty_reason`, почему требований нет (оглавление, история изменений). Ни одной страницы без записи в `coverage`.

**Аналитик B - по сценариям пользователя:**

> Иди не по порядку документа, а по сценариям: кто пользователь, как попадает в фичу, что делает по шагам, какие развилки, что видит при ошибке, что уходит на бэк. Смотри глазами тестировщика: что будет, если пусто, если нет сети, если отменил посреди, если условие на границе, если у пользователя несколько ролей или аккаунтов. `coverage` - по сценариям: `section` - название сценария, `pages` - где он описан. Если по сценарию в материалах нет ответа - это `ambiguities` или `missing_refs`, не догадка.

## 3. Проверка цитат - скрипт

```
node <папка скилла>/scripts/check-quotes.mjs <feature>/source \
  <feature>/intake/analyst-a.json <feature>/intake/analyst-b.json \
  > <feature>/intake/quote-check.json
```

Статусы: `ok`, `wrong_page` (цитата есть, страница не та), `not_found` (выдумана или искажена), `file_missing`. Выход с кодом 1 при любой проблеме - это нормально, отчёт всё равно записан. Невалидный JSON у аналитика - вернуть ему ошибку тем же субагентом (SendMessage), не чинить руками.

## 4. Судья

Субагент, `model: fable`. Дать: пути к `source/`, `analyst-a.json`, `analyst-b.json`, `quote-check.json`.

**Большой разбор** (у аналитиков вместе больше ~250 требований или отчёты больше ~300 КБ): нарезать отчёты по диапазонам страниц по границам разделов ТЗ и запустить до трёх судей параллельно, каждому свой диапазон, "пройди свои страницы сам" - только по нему. Записи без страниц (из JSON и md) - первому судье вместе с этими файлами. Номера у судей локальные (`J1-001`), потом склейка со сквозной нумерацией:

```
node <папка скилла>/scripts/split-by-pages.mjs <out>/split 1-11,12-29,30-41 <report-1.json> <report-2.json>
node <папка скилла>/scripts/merge-judges.mjs <out>/judge-1.json <out>/judge-2.json <out>/judge-3.json > <out>/judge.json
```

Для масштаба: на ТЗ в 41 страницу аналитики дают ~460 и ~290 требований, ~630 КБ, это три судьи. Не говорить судье, какой аналитик шёл каким заходом, и называть отчёты "первый" и "второй" (`report-1`, `report-2`) в случайном порядке, без поля `analyst`: чтобы не доверял одному заранее.

Задание (дословно, подставив пути):

> Два аналитика независимо разобрали одни материалы. Их результаты и отчёт скрипта о проверке цитат - по путям ниже. Материалы - в `<source>`. Твоя задача - собрать один проверенный реестр требований. Цитаты твоего файла тоже проверит скрипт.
>
> 1. Записи со статусом `not_found` в отчёте - не верь им. Открой материалы, найди, есть ли такое требование на самом деле. Есть - бери с правильной цитатой. Нет - в `rejected`.
> 2. Сопоставь записи двух аналитиков: одно и то же требование / нашёл только один / поняли по-разному.
> 3. Для каждой записи проверь, что цитата **действительно говорит то**, что написано в `statement`, а не просто существует. Не следует - исправь формулировку (`verdict: corrected`) или в `rejected`.
> 4. "Нашёл только один" и "поняли по-разному" - перечитай это место сам. Подтвердилось - в реестр. Можно понять двумя способами - в `ambiguities`. **Не выбирай прочтение сам** - это решает человек.
> 5. Пройди материалы по разделам сам и найди требования, которые пропустили оба. Такие - в `gaps` и в реестр с `found_by: "judge"`.
> 6. Противоречия и ссылки на отсутствующее - сведи без дублей.
>
> Запиши `<путь>/intake/judge.json`:
> ```json
> {
>   "registry": [{ "id": "ТЗ-001", "type": "", "statement": "", "sources": [{ "file": "", "page": 0, "quote": "" }], "found_by": "both | first | second | judge", "verdict": "confirmed | corrected", "from": ["A-001", "B-014"], "note": "" }],
>   "rejected": [{ "from": "B-022", "reason": "not_found | not_supported | misread", "detail": "" }],
>   "ambiguities": [{ "id": "AMB-1", "scenario": "часть сценария - экран и момент", "what_happens": "что делает пользователь и что видит, обычными словами", "sources": [], "readings": [], "why_it_matters": "", "who_can_answer": "user | analyst | backend | designer" }],
>   "conflicts": [{ "id": "CON-1", "scenario": "часть сценария - экран и момент", "what_happens": "что делает пользователь и что видит, обычными словами", "sources": [], "note": "", "why_it_matters": "что увидит пользователь приложения при каждом из вариантов", "who_can_answer": "" }],
>   "gaps": [{ "id": "GAP-1", "registry_id": "ТЗ-0NN", "note": "что пропустили оба" }],
>   "missing_refs": [{ "id": "REF-1", "sources": [], "what": "" }],
>   "agreement": { "both": 0, "first_only": 0, "second_only": 0, "misread": 0 },
>   "uncovered": [{ "pages": "", "note": "страницы, по которым ни у кого нет записей и нет причины" }]
> }
> ```
> `ТЗ-NNN` - по порядку документа. Каждая запись - с дословной цитатой. Двусмысленности и противоречия пиши для человека, который не читал ТЗ и не знает фичу: без номеров и имён полей вместо объяснения. В ответе мне - путь к файлу и числа из `agreement`, `rejected`, `ambiguities`, `conflicts`, `gaps`.

Потом тот же скрипт по `judge.json`. Проблемные цитаты судьи - вернуть ему (SendMessage) на исправление, один круг; не исправилось - пометить запись в реестре "цитата не подтверждена" и сказать пользователю.

## 4б. Сортировка вопросов

Судья отдаёт десятки пунктов (на ТЗ в 41 страницу - около 80). Пользователю столько не отдавать: не прочитает. Отдельный субагент, `model: opus`, свежий контекст. Дать: `judge.json`, пути к `source/`.

Задание (дословно, подставив пути):

> В `<путь judge.json>` - проверенный разбор ТЗ: двусмысленности (`ambiguities`), противоречия (`conflicts`), ссылки на отсутствующее (`missing_refs`), непокрытые страницы (`uncovered`), пропуски обоих аналитиков (`gaps` - бери только те, что не повторяют пункт из других списков). Материалы - `<source>`. Отсортируй каждый пункт, чтобы человек получил только то, без чего нельзя начинать.
>
> По каждому пункту:
> - `severity`:
>   - `blocker` - от ответа меняется то, что строим: сценарий пользователя, что отправляем на бэк и кто это формирует, контракт API, правило, по которому пользователь получит отказ. Ставь скупо: сомневаешься между `blocker` и `important` - `important` с вариантом по умолчанию.
>   - `important` - поведение на краю, тексты ошибок, лимиты, порядок полей; можно начать с варианта по умолчанию и уточнить по ходу.
>   - `minor` - опечатки и невалидный JSON в примерах, ссылки на макеты и тикеты без требований внутри, то, что однозначно закрывается соседним текстом ТЗ или ответом бэка.
> - `who` - кто может ответить: `user` (владелец задачи решает сам: поведение приложения там, где ТЗ молчит, UX), `analyst` (бизнес-правила, противоречия внутри ТЗ), `backend` (контракт API, что отдаёт и принимает бэк), `designer` (состояния и вид экранов).
> - `default` - что делаем, если ответа не будет: конкретно, со ссылкой на то, на что опираемся (пример ТЗ, ответ бэка, существующая версия продукта).
> - `why` - на что влияет, одной фразой простыми словами.
> - `question` - вопрос простым языком, одно-два предложения, без имён полей вместо объяснения; страница ТЗ в скобках.
> - Пункты об одном и том же - сливай: `merge` - список id, которые поглощены этим пунктом.
>
> Запиши `<путь>/triage.json`: `{ "items": [{ "id": "", "severity": "", "who": "", "why": "", "default": "", "question": "", "merge": [] }] }` - по каждому пункту судьи ровно одна запись (поглощённые - только в `merge`). В ответе мне - путь и счёт по `severity` × `who`.

Как раскладывать:
- **Пользователю в сообщение** (шаг 6) - все `blocker`, кому бы ни адресованы (с пометкой, кто ответит), и `important` с `who: user`. Больше 10 - первые 10 по влиянию, остальные одной строкой "ещё N, предлагаю по умолчанию…".
- **Опросник** - `blocker` и `important` с `who: analyst` и `backend` - в `intake/questions-<who>.md`; пользователю предложить `/to-questionnaire`.
- **Дизайнеру** - пункты с `who: designer` уходят в ревизию макетов (шаг 7), корзина "дизайнеру".
- **Принято по умолчанию** - всё `minor` и `important` с `default`, не вошедшее выше: списком в `00-intake-<feature>.md`, у записей реестра пометка "по умолчанию: …". Пользователю одной строкой, сколько.

## 5. Реестр и файл разбора

Реестр - скриптом:

```
node <папка скилла>/scripts/render-registry.mjs <feature>/intake/judge.json "Реестр требований: <фича>" > <feature>/requirements.md
```

Колонки `ID | Требование | Источник | Цитата | Нашли | Где в PRD | Тикет`; последние две пустые, их заполняют `/spec-check` и `/ticket-check`. Номера `ТЗ-NNN` дальше не меняются: PRD, тикеты и тесты ссылаются на них. Новое требование при повторном прогоне - следующим свободным номером.

**`00-intake-<feature>.md`:**
- **Шапка** - строка `**Размер:** M` или `L`, принятый с пользователем. По ней следующие скиллы выбирают режим; при переходе в полный - поправить.
- **Источники** - что прочитано (из `sources_read`), чего нет (`missing_refs`).
- **Выжимка** - основной сценарий в 5-7 шагов и экраны по строке, каждый пункт со ссылкой на `ТЗ-NNN`. Группировка по экранам и частям фичи, не по порядку ТЗ.
- **Что уже есть в проекте** - по коду, коротко: что переиспользуем, что похожее уже сделано.
- **Вопросы** - из `ambiguities`, `conflicts`, `missing_refs`, `uncovered`.
- **Ревизия макетов** - шаг 7.
- **Решено пользователем** - ответы, с датой.

## 6. Вопросы → ⛔ СТОП

Одно сообщение пользователю:

- **Как понял** - 5-7 простых предложений: что за фича, кто пользуется, основной сценарий.
- **Качество разбора** - одной строкой: сколько требований, сколько нашли оба, сколько отклонено как выдуманное или неверно понятое.
- **Вопросы** - только отобранные на шаге 4б (до 10), списком заголовков, чтобы был виден объём. Потом по одному за сообщение **по "Формату находки" из CLAUDE.md**: что происходит в приложении, что в ТЗ дословно, в чём вопрос, чем грозит, что предлагаю по умолчанию, кто ответит, если не пользователь.
- **Остальное** - одной-двумя строками: "N вопросов аналитику и бэку собраны в опросник, M мелочей принято по умолчанию (список в файле разбора)".

Вопросов, на которые может ответить только аналитик, больше двух - предложить пользователю запустить `/to-questionnaire`: соберёт опросник файлом.

Ждать. Ответы - в "Решено пользователем" с датой, затронутые записи реестра - поправить с пометкой "решено пользователем, дата". Пока вопросы, меняющие сценарий, без ответа, дальше не идти. Оставленные аналитику - в "Открытые вопросы", потом строкой `Д-N` в PRD.

## 7. Ревизия макетов → ⛔ СТОП

Отдельный проход по каждому экрану: что дизайнер мог забыть. Чек-лист на каждый экран:

- состояния: пустое, загрузка, ошибка, успех;
- обрыв сети на действии и повтор;
- отмена и "назад" посреди флоу - что с введённым;
- валидация ввода и тексты ошибок;
- роли и несколько аккаунтов - кто что видит;
- тупиковые ветки сценария;
- расхождение с существующей версией продукта (веб, старый экран) и с уже сделанными частями (статус у одной роли должен сходиться с действием другой);
- аналитика: какие события трекать (система аналитики - из `workflow.md`).

Формат: экран → до 5 пунктов, каждый в одну строку, по трём корзинам: дизайнеру / аналитику и бэку / так задумано или закрываем сами. Пользователь по каждому решает. Решения - в файл.

## 8. Передать дальше

Одной строкой: "intake готов: N требований в реестре, M вопросов закрыто, K ушло аналитику". Дальше `/grill-with-docs` только по спорному: что закрыто в "Решено пользователем" и в реестре, гриль заново не спрашивает. PRD ссылается на `ТЗ-NNN`.

## Скрипты и их тест

`scripts/check-quotes.mjs` - проверка цитат, `split-by-pages.mjs` и `merge-judges.mjs` - нарезка и склейка для нескольких судей, `render-registry.mjs` - реестр, `check-eval.mjs` - счёт эвала, `pdf-to-text.sh` - текст из PDF. После любой правки `check-quotes.mjs` - контрольный тест на синтетическом ТЗ с известными ответами:

```
node --test <папка скилла>/scripts/test/check-quotes.test.mjs
```

Скрипт ошибся на реальном прогоне (ложная тревога или пропуск) - сначала случай в `scripts/test/cases.json` и строчку в `test/source/tz.txt`, тест красный, потом правка скрипта.

## Режим эвала

`/intake eval <NNN>` - проверка самого скилла на прошлом проколе. Кейсы живут в проекте, не в скилле (в них внутренние ТЗ): папка эвалов из `workflow.md`, по умолчанию `docs/agents/intake-evals/`, формат - [evals/README.md](evals/README.md).

Шаги 1-4 на `source_dir` из `expected.json` кейса, в папку фичи ничего не писать, пользователю вопросов не задавать. Рабочие файлы субагентов - в нейтральную папку в скратчпаде сессии (`feature-run/`), **не** рядом с кейсами: путь со словом `evals` подсказывает, что это проверка, а рядом лежат ответы. После прогона скопировать всё в `<папка эвалов>/runs/<дата>-<NNN>/`. Потом `scripts/check-eval.mjs` по `judge.json` и `expected.json`, счёт и качество цитат - строкой в таблицу "Прогоны" и пользователю. Аналитикам и судье не говорить, что это эвал и что ищем: иначе проверка ничего не стоит.

## Чего не делать

- Не анализировать ТЗ в главной сессии и не дописывать за аналитиков - только раздать, проверить, собрать.
- Не давать субагентам разговор, выжимку или глоссарий - только `source/` и их же файлы.
- Не верить цитате без прогона скрипта - ни аналитика, ни судьи.
- Не выбирать прочтение двусмысленности - это вопрос пользователю.
- Не начинать гриль, глоссарий или PRD, пока вопросы, меняющие сценарий, без ответа.
- Не вываливать пользователю весь реестр - только "как понял", качество одной строкой и вопросы.
