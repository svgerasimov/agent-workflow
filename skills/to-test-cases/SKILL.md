# Skill: тест-кейсы для тестировщика

Пишутся на языке пользователя. Папки и формат номера тикета трекера - из `docs/agents/workflow.md`.

## Два режима

**Единица тест-кейсов - тикет трекера (Jira и т.п.), а не тикет реализации.** Тест-кейсы прикрепляются к тикету трекера; сколько тикетов трекера, столько файлов.

| Режим | Когда | Что на выходе |
|---|---|---|
| **на фичу** (по умолчанию) | фича едет одним тикетом трекера | один файл `test-cases/<TICKET-ID>-<feature>.md` на всю фичу |
| **на задачу** | фича разбита на несколько тикетов трекера | `test-cases/<NN>-<slug>.md` по конкретному тикету реализации |

Почему по умолчанию "на фичу":
- тикеты реализации нарезаны по швам кода, тестировщик идёт по экранам; на инфраструктурный слайс наблюдаемого поведения нет вообще;
- тест-кейсы к раннему слайсу описывают промежуточное состояние, которое поздний слайс отменяет; файл на фичу всегда про конечное состояние;
- один тикет трекера - одно вложение, общие предусловия пишутся один раз;
- дыры в покрытии видны, когда сценарии лежат подряд, а группировка по экранам переживает фичу и годится для регресса.

## Входные данные

Аргумент:
- имя фичи или пусто → режим "на фичу" по фиче в работе. Файл уже есть - **дописывать в него**;
- номер тикета реализации или путь → в режиме "на фичу" дописать блоки по нему; в режиме "на задачу" - отдельный файл;
- `на-задачу` с номером → принудительно режим "на задачу".

Непонятно, один тикет трекера на фичу или несколько, - спросить одним вопросом.

Прочитать:
1. Тикет реализации - "Критерии приёмки" задают минимальное покрытие.
2. Разделы PRD, на которые тикет ссылается: функциональные требования, краевые случаи, тексты ошибок.
3. Спеки макетов из тикета - точные тексты, состояния кнопок, видимость блоков.

**Не выдумывать поведение.** Чего нет ни в PRD, ни в спеке, ни в тикете, не превращать в ожидаемый результат. Не хватает данных (стенд, учётка, ответ бэка) - в "Предусловия" или "Открытые вопросы".

## Куда писать

- "на фичу": `<папка фич>/<feature>/test-cases/<TICKET-ID>-<feature>.md`;
- "на задачу": `<папка фич>/<feature>/test-cases/<NN>-<slug>.md`, тот же `NN` и `slug`, что у тикета.

## Формат файла

Шапка - один раз. **Кейсы группируются по экранам флоу** в порядке прохождения, не по номерам тикетов. Нумерация сквозная (`ТК-01`, `ТК-02`, …), при дозаписи продолжается, старые номера не переприсваиваются: на них ссылаются баги.

```markdown
# Тест-кейсы: <название фичи для тестировщика>

**Статус:** на-разбор
**Тикет:** <TICKET-ID>
**Фича:** <feature>
**Связано:** 01-prd-<feature>.md, <спеки>
**Покрытые тикеты:** tickets/<NN>-<slug>.md, ...

## Общие предусловия

<Что верно для всех кейсов: сборка или стенд, учётная запись, путь до раздела.>

## <Экран 1 - как он называется для пользователя>

### ТК-01 <что проверяем>

**Приоритет:** высокий | средний | низкий
**Тип:** позитивный | негативный | граничный | регресс
**Предусловия:** <только специфичные для кейса>
**Основание:** <раздел PRD / ТЗ-NNN / спека>

| # | Шаг | Ожидаемый результат |
|---|-----|---------------------|
| 1 | <действие> | <что видит> |

## Прослеживаемость

| Критерий приёмки | Тикет | Кейсы |
|---|---|---|
| <критерий> | <NN> | ТК-01, ТК-03 |

## Открытые вопросы

- <чего не хватает для проверки>
```

## Дозапись

- прочитать файл целиком, дописывать в существующие секции экранов; новую секцию - только для нового экрана;
- нумерация продолжается;
- дополнить "Прослеживаемость" и "Покрытые тикеты";
- **пересмотреть старые кейсы**: слайс изменил описанное поведение - поправить старый кейс, а не добавлять противоречащий.

## Правила покрытия

- **Каждый критерий приёмки покрыт хотя бы одним кейсом.** Таблица "Прослеживаемость" обязательна.
- Порядок: позитивные, негативные, граничные, регресс.
- Негативные и граничные - в первую очередь из краевых случаев PRD, ссылкой на них.
- Регресс - 1-3 кейса "что рядом не должно сломаться".
- Тексты ошибок и подписи - **дословно** из PRD и спеки.
- Поведение различается по платформам - отдельные кейсы с пометкой платформы или строка "Платформы: ..." в предусловиях.
- Один кейс - одна проверка.
- Приоритет: высокий - ломает основной сценарий или теряет данные; средний - видимый дефект без потери данных; низкий - косметика.

## Чего не делать

- Не писать кейсы на логику, покрытую автотестами: тестировщик проверяет через UI.
- Не писать про внутренности в терминах кода - только наблюдаемое поведение.
- Не менять тикет, PRD и спеки.
- Не плодить файл на каждый тикет реализации, когда фича едет одним тикетом трекера.
- Не группировать секции по слайсам - только по экранам.
