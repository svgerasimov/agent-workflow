# Skill: перепроверка тикетов

Зачем: тикеты режутся по PRD на момент нарезки. Потом PRD правят (`/spec-check`, ответы аналитика, решения по ходу), а тикеты остаются старыми - и `/implement` с судьями сверяет код со старым тикетом.

Запускать в чистом контексте (новая сессия или после `/clear`): проверке не нужен разговор, ей нужны файлы.

Пути и команды проекта - в `docs/agents/workflow.md`; нет файла - предложить `/setup-workflow`.

Все ответы пользователю - на языке пользователя, простым языком, как в "Формате общения" CLAUDE.md.

## 0. Взять фичу

Аргумент - имя фичи. Без аргумента - фича в работе по `workflow.md`. Неоднозначно - спросить.

Нужны в `<папка фич>/<feature>/`: `requirements.md` (реестр из `/intake`), `01-prd-<feature>.md`, тикеты `tickets/` (открытые) и `tickets/done/` (закрытые). Реестра нет - остановиться и предложить сначала `/intake`: без него сверять не с чем, кроме пересказа.

Тикет со статусом "в-работе" - сказать пользователю: по нему проверка может поменять критерии посреди работы.

## 1. Судьи

Свежие субагенты, Agent tool, general-purpose, `model: opus`. Разговор не передавать - только пути: реестр, PRD, папка тикетов, спеки макетов (папка из `workflow.md`), на которые ссылаются тикеты, текст ТЗ в `source/*.txt` (чтобы открыть цитату, если формулировка реестра вызывает сомнение).

Реестр до ~150 записей - один судья. Больше - по диапазонам номеров (`ТЗ-001…ТЗ-150`, …) по границам разделов, до трёх параллельно; каждый видит все тикеты.

Задание (дословно, подставив пути и диапазон):

> Ты проверяешь, что тикеты фичи покрывают требования и не устарели. Реестр требований - `<requirements.md>` (номера `ТЗ-NNN`, у каждого цитата ТЗ). PRD - `<путь>`. Тикеты - `<папка tickets/>`: открытые в корне, закрытые в `done/`. Текст ТЗ - `<путь .txt>`, размечен `=== PAGE N`. Твой диапазон реестра: `<ТЗ-xxx…ТЗ-yyy>`.
>
> 1. **Покрытие.** Для каждого номера диапазона: в каком тикете это требование реализуется или реализовано (номер тикета, открыт или закрыт), или в PRD записано "не входит" / `Д-N` / "так задумано" (раздел), или **нигде**. Не ищи совпадение слов - ищи, чей критерий приёмки или "Что делаем" это поведение покрывает.
> 2. **Открытые тикеты** (корень папки). По каждому:
>    - критерий приёмки, который расходится с реестром или PRD - что именно и где правда (номер `ТЗ-NNN`, раздел PRD);
>    - устаревшее: тикет говорит то, что PRD уже поменял (сравни с текущим PRD, особенно разделы с датами решений и "Решённые вопросы");
>    - неполнота: требования реестра, которые по смыслу относятся к этому тикету, но в критериях их нет;
>    - блокеры: тикет ждёт то, что уже закрыто, или не ждёт то, без чего не сделать.
> 3. **Закрытые тикеты** (`done/`) - не переоценивай их код. Только: требование реестра, которое по смыслу должен был покрыть закрытый тикет, а в его критериях его нет, - в `uncovered` с пометкой, какой закрытый тикет был ближе всего.
>
> Каждая находка - с цитатой ТЗ (дословно, 5-25 слов, `file`, `page`): её проверит скрипт. Ничего не исправляй.
>
> Запиши `<путь>/ticket-check/judge-<N>.json`:
> ```json
> {
>   "range": "ТЗ-001…ТЗ-150",
>   "coverage": [{ "id": "ТЗ-001", "where": "ticket | prd | nowhere", "ticket": "07", "state": "open | done | null", "prd": "раздел или null" }],
>   "uncovered": [{ "id": "ТЗ-0NN", "nearest_ticket": "07", "scenario": "часть сценария - экран и момент", "what_happens": "что делает пользователь и что видит по ТЗ, обычными словами", "risk": "что будет, если требование так и не сделать", "sources": [{ "file": "", "page": 0, "quote": "" }] }],
>   "ticket_findings": [{ "ticket": "08", "kind": "conflict | outdated | incomplete | blockers", "scenario": "часть сценария - экран и момент", "what_happens": "что делает пользователь и что видит по ТЗ/PRD", "ticket_says": "что в тикете - дословно", "detail": "в чём расхождение и где правда", "risk": "что увидит пользователь приложения, если сделать по тикету как есть", "registry": ["ТЗ-0NN"], "prd": "раздел", "sources": [{ "file": "", "page": 0, "quote": "" }] }]
> }
> ```
> `coverage` - по **каждому** номеру диапазона. Находки пиши для человека, который не читал ни ТЗ, ни PRD, ни тикеты: без номеров и имён полей вместо объяснения. Тикет читай целиком, включая `## Комментарии`. В ответе мне - путь к файлу и счёт: покрыто тикетами / PRD / нигде, находок по открытым тикетам по видам.

Цитаты судей - `node <папка скилла intake>/scripts/check-quotes.mjs <source> <judge-*.json>`; ненайденные - судье на исправление, один круг.

## 2. Проверить находки

Судья ошибается так же, как нарезка. Каждую находку открыть самому: тикет, место в PRD, цитату в ТЗ. Ложные - выкинуть, пользователю одной строкой сколько. Дубли между судьями - склеить.

## 3. Показать пользователю → ⛔ СТОП

Сначала одной-двумя строками итог: сколько требований покрыто тикетами, сколько PRD, сколько нигде. Дальше находки - **по "Формату находки" из CLAUDE.md**, по одной за сообщение: что происходит в приложении, что в ТЗ дословно, что в тикете, в чём проблема, чем грозит, что предлагаю. Порядок: открытые тикеты, которые меняют то, что отправляем на бэк, или уже в работе; потом остальное; потом требования ТЗ, которых нет ни в одном тикете (с ближайшим тикетом). Тикет перед находкой читать целиком, включая `## Комментарии`.

По каждой находке пользователь решает:
- **поправить тикет** - критерии приёмки и "Что делаем";
- **новый тикет** - для непокрытого, если не влезает в открытый или ближайший закрыт;
- **так задумано** - в PRD рядом с решением цитата ТЗ и причина, чтобы следующая проверка не поднимала.

Ждать. Не править тикеты до решения.

## 4. Внести

- Правки открытых тикетов - по решениям, в шапке тикета строка в `## Комментарии`: дата, что поменяла проверка, номера `ТЗ-NNN`.
- Новые тикеты - следующими свободными номерами, по шаблону тикетов фичи, со ссылками на `ТЗ-NNN`, статус `на-разбор`.
- Закрытые тикеты не трогать.
- В `requirements.md` - колонка "Тикет" по `coverage`. Номер без тикета и без решения в PRD - дыра, пользователю.
- Отчёт - `<папка фич>/<feature>/ticket-check.md`: дата, число судей, счёт покрытия, таблица находок с решением. Повторный прогон - новым блоком сверху.

## Чего не делать

- Не давать судьям разговор, выжимку или GLOSSARY - только файлы.
- Не править тикеты и PRD до решения пользователя.
- Не переоценивать код закрытых тикетов - это `/code-review`, не эта проверка.
- Не считать совпадение слов покрытием: покрывает критерий приёмки, а не упоминание.
